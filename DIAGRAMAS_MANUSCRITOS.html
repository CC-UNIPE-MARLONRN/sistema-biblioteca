A) Escolha uma função pura implementada e explique por que possui transparência referencial.
A função Relatorios.calcularMulta(diasAtraso, multaDiaria) é pura porque: • Recebe parâmetros (long, BigDecimal) e retorna BigDecimal (multiplicação) • Mesmas entradas SEMPRE produzem a mesma saída (ex.: 3 dias × R$ 2,00 = R$ 6,00) • NÃO altera objetos, listas, nem estado da biblioteca • NÃO tem efeitos colaterais (não escreve, não imprime, não modifica estado global) Por isso possui TRANSPARÊNCIA REFERENCIAL: a chamada pode ser substituída pelo valor retornado (6.00) sem alterar o comportamento do programa.
B) Identifique uma operação impura e explique por que não é uma função pura.
Biblioteca.emprestar(idEmp, idLiv, idUsu, dtEmp, dtPrev) é IMPURA porque: 1. ALTERA o estado da biblioteca: insere novo Emprestimo no mapa 'emprestimos' 2. Resultado DEPENDE do estado atual: se livro já tem empréstimo ativo → exceção; se não tem → sucesso. Mesma entrada, resultados diferentes conforme estado. 3. Tem EFEITO COLATERAL visível externamente (o mapa interno muda) 4. Não é determinística apenas pelos argumentos → não é função pura.
C) Explique como a imutabilidade foi aplicada e quais problemas ajuda a evitar.
COMO FOI APLICADA: • Livro, Usuario, Emprestimo: todos atributos private final (imutáveis após construção) • Emprestimo.devolver(data): NÃO modifica o objeto; CRIA e RETORNA novo Emprestimo com dataDevolucao preenchida (padrão imutável) • Biblioteca.obterDados(): retorna DadosBiblioteca com listas unmodifiableList • Relatorios: todas funções retornam novas coleções/cópias; NUNCA alteram entradas PROBLEMAS QUE EVITA: • Efeitos colaterais acidentais: consulta não corrompe estado da biblioteca • Bugs de concorrência: objetos imutáveis são thread-safe por natureza • Aliasing inesperado: passar lista para função não permite modificação • Dificuldade de raciocínio: código puro é mais fácil testar, depurar, manter • Violação de encapsulamento: estado interno da Biblioteca não vaza mutável

D) Compare as versões imperativa e funcional quanto à legibilidade, manutenção, imutabilidade e efeitos colaterais.
Funcionalidade comparada: emprestimosAtrasados (funcional) vs emprestimosAtrasadosImperativo (imperativa) | Critério | Funcional (filter) | Imperativa (for + if) | |-----------------|---------------------------------|------------------------------| | Legibilidade | Expressa O QUÊ (critério) | Expressa COMO (passos) | | Manutenção | Fácil encadear .filter()/.map() | Edita corpo do laço | | Imutabilidade | Garantida (stream + collect) | Neste projeto cria lista nova| | Efeitos colat. | Nenhum (pipeline puro) | Permite mutação acidental | | Composição | Natural (saída → entrada) | Variáveis intermediárias | VERIFICAÇÃO NO MAIN: identificadores(funcional).equals(identificadores(imperativo)) → TRUE
E) Se dois usuários tentarem emprestar simultaneamente o mesmo livro, qual problema pode ocorrer? Funções puras e imutabilidade bastam para evitá-lo? Justifique.
PROBLEMA: Race Condition (condição de corrida). Cenário: Thread A e Thread B chamam emprestar("E1", "L1", ...) quase junto: 1. Thread A verifica: livroEmprestado = false (livre) 2. Thread B verifica: livroEmprestado = false (Ainda livre — A não registrou) 3. Thread A registra empréstimo E1 4. Thread B registra empréstimo E2 5. RESULTADO: DOIS empréstimos ativos para o mesmo livro → VIOLA REGRA DE NEGÓCIO FUNÇÕES PURAS E IMUTABILIDADE NÃO BASTAM para evitar: • Funções puras não têm efeitos colaterais, mas NÃO coordenam escritas concorrentes • Imutabilidade protege LEITURAS, mas o estado mutável da Biblioteca (mapa emprestimos) precisa de sincronização na ESCRITA • O problema é de SINCRONIZAÇÃO DE ESTADO COMPARTILHADO, não de pureza SOLUÇÃO IMPLEMENTADA: Biblioteca.emprestar(...) é synchronized → verificação de disponibilidade + registro no mapa ocorrem ATOMICAMENTE. Teste em Main.verificarConcorrencia(): 2 threads tentam → EXATAMENTE 1 é aceita.
